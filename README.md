# Rillza VPN — Telegram bot

Телеграм-бот для продажи VPN-подписок. База данных — источник правды,
панель [CELERITY](https://github.com/ClickDevTech/CELERITY-panel) —
исполнитель, клиентское приложение — [Happ](https://happ.su).

Состояние работы для следующей сессии: [handoff.json](handoff.json).
План разработки и все принятые решения: [PLAN.md](PLAN.md).
Настройка окружения: [docs/SETUP.md](docs/SETUP.md).
Незакрытые находки ревью: [docs/REVIEW.md](docs/REVIEW.md).

## Стек

Python 3.13 · aiogram 3 · PostgreSQL + SQLAlchemy 2 (asyncpg) · Redis ·
APScheduler · loguru · uv · Docker Compose

## Что умеет

- Пробный период на 3 дня, один раз на аккаунт
- Подписки на 1/3/6/12 месяцев, оплата картой (ЮMoney) и криптой
  (CryptoBot); цены и продажа тарифов правятся из админки без деплоя
- Экран подписки с живым трафиком и инструкцией подключения в три шага
- Напоминания за 3 дня и за сутки до окончания
- Админка: статистика, карточка пользователя, выдача и отзыв доступа,
  тарифы (цена и снятие с продажи), рассылки
- Анонимная поддержка: пользователь пишет из меню, админ отвечает
  реплаем, отправитель остаётся невидимым

## Быстрый старт

```bash
cp .env.example .env
# заполнить BOT_TOKEN, ADMIN_IDS, POSTGRES_PASSWORD, DATABASE_URL, PANEL_API_KEY
docker compose up -d --build
docker compose logs -f bot
```

Откуда брать каждую переменную и чем проверить результат —
[docs/SETUP.md](docs/SETUP.md).

## Локальная разработка

```bash
uv sync                    # поставить зависимости
uv run ruff check .        # линт
uv run ruff format .       # форматирование
uv run pytest              # тесты (интеграционные пропускаются без БД)
uv run alembic upgrade head  # применить миграции
uv run python -m app       # запуск бота (нужны Postgres и Redis)
```

Интеграционные тесты требуют настоящий PostgreSQL — SQLite игнорирует
`FOR UPDATE`, и проверки блокировки платежей проходили бы впустую:

```bash
createdb rillza_test
TEST_DATABASE_URL=postgresql+asyncpg://postgres@localhost:5432/rillza_test \
  uv run pytest
```

Миграции применяются автоматически при старте контейнера
(`docker-entrypoint.sh`). Новые создаются так:

```bash
uv run alembic revision --autogenerate -m "что изменилось"
uv run alembic check   # проверить, что модели и миграции сошлись
```

## Проверочные скрипты

Оба только читают: ничего не создают, не меняют и не списывают. Возвращают
код `0` при успехе и `1` при проблеме, так что годятся для деплой-скрипта.

```bash
uv run python -m scripts.check_panel      # доступность, ключ, группа, лимит устройств
uv run python -m scripts.check_payments   # кому принадлежат платёжные токены

docker compose exec bot python -m scripts.check_panel      # то же в контейнере
docker compose exec bot python -m scripts.check_payments
```

Лимит устройств живёт на группе, а `GET /api/groups` отдаёт только id и
имя — поэтому `check_panel` читает его через существующий аккаунт и
отдельно показывает, у скольких аккаунтов задан свой `maxDevices`. Это
норма для аккаунтов, которыми управляет бот: он ставит `maxDevices`
явно (2 или 4) на каждом из них, а лимит группы — лишь запасное
значение для аккаунтов, которыми бот не управляет. Пока на панели нет
ни одного аккаунта, проверка честно говорит, что сказать нечего.

## Настройки

Все переменные окружения перечислены в [.env.example](.env.example).
Обязательные: `BOT_TOKEN`, `DATABASE_URL`, `PANEL_BASE_URL`,
`PANEL_API_KEY`. Админка открывается тем, кто перечислен в `ADMIN_IDS`.
Оплата включается наличием ключей: `YOOMONEY_ACCESS_TOKEN`
для карт и `CRYPTOBOT_TOKEN` для криптовалюты — провайдер без ключа просто
не показывается на экране покупки. Логирование в Telegram-чат включается
парой `LOG_BOT_TOKEN` + `LOG_CHAT_ID` — формально необязательной, но на
сервере без присмотра это единственный сигнал об отказе панели, который
никак иначе не виден: healthcheck при этом остаётся зелёным. Подробности
и способ проверить доставку — в [docs/SETUP.md](docs/SETUP.md).

## Разовая настройка панели CELERITY

Панель разворачивается отдельно; боту нужно от неё следующее:

1. **API-ключ** — Settings → Security → API Keys, скоупы `users:read`,
   `users:write`, `stats:read`. Значение в `PANEL_API_KEY`.
2. **Серверная группа** (по умолчанию `Celerity Primary Access`) с
   `maxDevices = 2` — все новые аккаунты привязываются к ней, а её
   лимит служит запасным значением для аккаунтов, которыми бот не
   управляет: свой лимит (2 или 4) бот ставит каждому аккаунту явно.
   Имя группы — в `PANEL_GROUP_NAME` и сверяется точно: если оно не
   совпадает, аккаунт создаётся вообще без группы и его VLESS не
   уезжает на ноду.
3. **Кнопка Happ** — Settings → Subscription → Buttons → кнопка `HAPP`
   с URL `happ://add/{url}`. Через неё подписка импортируется в
   приложение в одно нажатие.
4. **HWID** — Settings → Subscription → Happ → hwid mode `permissive`.
5. **Soft-block** (рекомендуется) — истёкшая подписка показывает
   понятный текст вместо ошибки.

## Эксплуатация

### Бэкапы

Теперь в базе лежат деньги и доступы: её потеря страшнее потери панели,
потому что панель восстанавливается из базы, а база — ниоткуда.

```bash
# ежедневный дамп; храните копию вне сервера
docker compose exec -T postgres pg_dump -U rillza rillza \
  | gzip > rillza-$(date +%F).sql.gz

# восстановление
gunzip -c rillza-2026-07-27.sql.gz \
  | docker compose exec -T postgres psql -U rillza rillza
```

Проверяйте восстановление хотя бы раз: непроверенный бэкап — это не бэкап.

### Фоновые задачи

| Задача | Интервал | Зачем |
|---|---|---|
| `payment_poller` | 30 c | проверяет выставленные счета |
| `provisioning_watcher` | 60 c | дожимает «оплачено, но не выдано» |
| `invoice_expirer` | 5 мин | закрывает просроченные счета |
| `expiry_sync` | 10 мин | помечает истёкшие подписки |
| `expiry_notifier` | 1 ч | напоминания за 3 дня и за сутки |
| `broadcast_resumer` | 5 мин | дописывает рассылку, прерванную рестартом |
| `reconciler` | 4 ч | приводит панель в соответствие с базой |
| `late_payment_sweep` | 24 ч | ищет деньги, пришедшие после закрытия счёта |

Состояние задач видно в админке: «📊 Статистика» показывает, когда каждая
последний раз отработала успешно. Если задача молчит больше часа —
смотрите логи, она упала.

### Если панель недоступна

Бот продолжает работать: экран подписки показывает даты из базы, платежи
принимаются и запоминаются. Доступ выдаётся, как только панель ответит —
`provisioning_watcher` и `reconciler` дожмут сами. Ничего перезапускать
не нужно, деньги не теряются.

### Если у пользователя не подключается

1. В админке откройте карточку пользователя → «🔄 Переподключить к
   серверам». Это `POST /api/sync` панели: её Xray-пуши идут без повторов,
   и это штатный способ починить одного клиента.
2. Проверьте статистику: если нода в списке офлайн, она молча исчезла из
   всех подписок — проблема не у клиента.
3. Если платёж завис в «оплачено, но не выдано» — кнопка «♻️ Повторить
   провижининг» в той же карточке.

### Возврат денег

Автоматического возврата нет намеренно. Порядок такой: отзовите доступ
кнопкой «⛔️ Отозвать» (аккаунт в панели остаётся отключённым, удалять
нельзя — пароль Hysteria выводится из ID, и пересоздание оживило бы
утёкшую ссылку), затем верните деньги вручную в кабинете ЮMoney или
CryptoBot. Запись о платеже в базе остаётся — это история, её не трогаем.
