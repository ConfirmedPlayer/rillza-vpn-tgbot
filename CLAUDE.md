# Rillza VPN — заметки для работы над проектом

Бот продаёт VPN-подписки. **База — источник правды, панель CELERITY —
исполнитель.** Всё остальное следует из этого: сначала пишем и коммитим
в базу, потом приводим панель в соответствие. Падение между этими шагами
оставляет `pending`-подписку, которую доделает следующая попытка, — но
никогда оплатившего человека без записи.

**Начинать с [handoff.json](handoff.json)** — состояние работы, живой
среды и ловушки, которых нет в коде. Он же обновляется перед уходом.

Проектные решения и их обоснование: [PLAN.md](PLAN.md).
Переменные окружения: [docs/SETUP.md](docs/SETUP.md).
Ревью перед запуском, всё закрыто: [docs/REVIEW.md](docs/REVIEW.md) —
исторический снимок с рассуждениями скептиков, не список дел.

## Команды

```bash
uv sync
uv run ruff check . && uv run ruff format .
uv run pytest                                   # без БД интеграционные пропускаются
TEST_DATABASE_URL=postgresql+asyncpg://postgres@localhost:5432/rillza_test \
  uv run pytest                                 # полный прогон
uv run alembic check                            # модели и миграции сошлись
uv run python -m scripts.check_panel            # панель: ключ, группа, лимит устройств
uv run python -m scripts.check_payments         # платёжные токены
```

Стиль: ruff, длина строки 79, одинарные кавычки. Кириллица в строках —
норма, RUF001-003 отключены.

## Что легко сломать, не заметив

**Устаревшие ORM-объекты.** Сессии создаются с `expire_on_commit=False`,
поэтому `SELECT ... FOR UPDATE` на строке, копия которой уже в сессии,
берёт блокировку и возвращает **дореблокировочные** значения. Любая
блокировка, от которой зависит корректность, обязана нести
`populate_existing=True`. Каждый UPDATE — compare-and-set с `RETURNING`.

**Решение по чтению вместо заявки.** Идемпотентность провижининга
держится на `payments.days_applied_at`. Правильно — *заявить* защёлку
условным UPDATE и действовать по результату; читать атрибут и решать по
нему нельзя, это уже приводило к двойному начислению дней.

**Панель CELERITY** (изучена по исходникам, не по документации):

- `userId` — это Telegram ID, ключ везде
- создание обязано слать `enabled: true` **и** `groups` одним POST:
  Xray-пуш идёт только для включённого пользователя и только по группам
  из этого же запроса, повторов и сверки у панели нет
- продление — абсолютный `expireAt`, никогда «текущий + N»
- отзыв — `enabled: false`. **DELETE не использовать никогда:** пароль
  Hysteria выводится из userId, пересоздание оживит утёкшую ссылку
- `POST /api/users/{id}/enable` не использовать: ничего не проверяет
- `GET /api/groups` отдаёт только `_id` и `name`; `maxDevices` группы
  виден лишь развёрнутым внутри пользователя
- `maxDevices` у пользователя `0` = наследовать группу, `-1` = безлимит;
  проверка работает только для Hysteria, по IP, и при ошибке пропускает
- одна ссылка подписки отдаёт и `hysteria2://`, и `vless://`

**Анонимность поддержки.** Только `copy_message`, никогда
`forward_message`. Пересылка раскроет владельца — это необратимо.

**Отсутствует намеренно:** анти-шеринг, автовозврат денег, сравнение
пришедшей суммы с ценой (ЮMoney p2p забирает 3% с перевода), удаление
аккаунтов в панели, трогание чужих аккаунтов при сверке.

## Тесты

Интеграционные требуют настоящий PostgreSQL: SQLite игнорирует
`FOR UPDATE`, и проверки блокировок проходили бы впустую.

**Тест на баг обязан падать на коде до правки.** Проверяется откатом:
убрать правку, увидеть падение, вернуть. В этом проекте уже была пара
тестов, которая проходила и на сломанном коде, то есть не проверяла
ничего.

## Работа с боевой панелью

Панель развёрнута отдельно и живая. Ломать, менять ноды и трогать чужие
аккаунты нельзя. Любое действие, меняющее состояние панели, — только
после явного разрешения владельца. Проверочные скрипты делают
исключительно GET и безопасны.

## Ветки

Разработка и пуш — в `master` (это ветка по умолчанию, не `main`).
