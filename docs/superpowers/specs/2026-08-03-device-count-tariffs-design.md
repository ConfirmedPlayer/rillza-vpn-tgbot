# Тарифы с числом устройств

**Дата:** 2026-08-03
**Статус:** согласовано с владельцем, к реализации не приступали

## 1. Задача

Человеку может не хватать двух устройств. Он должен иметь возможность
купить больше — сам, из бота, без обращения к владельцу.

Побочно закрывается давняя просьба: бот нигде не говорит, на сколько
устройств рассчитана подписка, кроме одной строки в `START`.

## 2. Решение одной фразой

Число устройств становится **свойством тарифа**. Рядом с четырьмя
существующими тарифами появляются четыре четырёхустройственных, покупка
идёт в два шага («сколько устройств» → «на какой срок»), а купленное
число хранится в `subscriptions.max_devices` и пушится в панель явным
числом вместо нынешнего `maxDevices: 0`.

## 3. Что отвергнуто и почему

| Вариант | Почему нет |
|---|---|
| Несколько подписок на пользователя | Решение владельца. `UNIQUE` на `subscriptions.user_id` остаётся, `panel_user_id` остаётся `str(telegram_id)` |
| Передача подписки другому человеку | Решение владельца, дословно: «про идею передать подписку другому — надо забыть» |
| Слоты устройств отдельным товаром | Отвергнуто в пользу «число устройств — свойство тарифа» |
| Слоты навсегда, разовой покупкой | Там же |
| Варианты на 6 и 8 устройств | Только 2 и 4. Спрос не подтверждён; редкий запрос закрывается ручной выдачей через админку |

## 4. Названный компромисс

Аккаунт с собственным `maxDevices` **перестаёт следовать группе**.
Менять лимит всем сразу, поправив группу в панели, больше нельзя —
после этой правки лимит каждого нашего пользователя задан персонально.

Принято сознательно: число в базе должно означать ровно то, что человек
купил, а не «то, что унаследовалось от текущей настройки группы».

Шесть аккаунтов, созданных владельцем вручную (`maxDevices = -1`), в
таблице подписок отсутствуют — сверка их только перечисляет и не
трогает. Это поведение не меняется.

## 5. Схема данных

### 5.1. Колонки

```
tariffs.max_devices        INTEGER NOT NULL DEFAULT 2
subscriptions.max_devices  INTEGER NOT NULL DEFAULT 2
```

`server_default = '2'` заполняет существующие строки при накате. Для
тарифов это правда по построению: четыре нынешних продаются на два
устройства. Для подписок — тоже: в панели у них `maxDevices = 0`,
что означает «наследовать группу», а у группы `Celerity Primary
Access` лимит равен 2.

Отдельного индекса не заводим. В таблице восемь строк, фильтр по
`max_devices` идёт вместе с `is_active` — существующего
`ix_tariffs_active_order` достаточно, а преждевременные индексы в этом
проекте уже отложены сознательно.

### 5.2. Сид

Миграция добавляет четыре строки. Цены — множитель 1.6 к нынешним:

| code | title_ru | duration_days | price_kopeks | max_devices | sort_order |
|---|---|---|---|---|---|
| `m1x4` | 1 месяц | 30 | 32 000 | 4 | 5 |
| `m3x4` | 3 месяца | 90 | 86 400 | 4 | 6 |
| `m6x4` | 6 месяцев | 180 | 153 600 | 4 | 7 |
| `m12x4` | 12 месяцев | 365 | 268 800 | 4 | 8 |

Ровный множитель выбран не только ради простоты. Ярлык «выгода N%» в
`keyboards.tariffs` считается от самого дорогого месяца в показанном
списке, поэтому при одном множителе лестница скидок в обоих наборах
совпадает: 0 / 10 / 20 / 31 %. Человек видит одну и ту же логику,
какой бы набор ни открыл.

Цены правятся из админки без деплоя — сид только заполняет пустое
место, как и `9f9809a15a9c`.

`downgrade()` удаляет строки по кодам и снимает колонки. Удаление
безопасно ровно до первой покупки такого тарифа: `payments.tariff_id`
ссылается на `tariffs.id`, и FK не даст удалить проданный тариф. Это
правильное поведение — откат миграции на базе с продажами должен
падать, а не терять историю платежей.

## 6. Контракт с панелью

### 6.1. Один PUT вместо двух

`CelerityClient.set_expiry` шлёт только `expireAt`. Переименовывается в
`set_state(panel_user_id, expire_at, max_devices)` и шлёт оба поля
одним `PUT /api/users/{id}`.

Причина против двух отдельных вызовов: панель не транзакционна. Два
PUT дают состояние «срок обновлён, лимит нет», которое живёт до
следующей сверки, то есть до четырёх часов.

`revoke` не трогаем: там намеренно только `enabled: false`.
`create_or_get_user` принимает `max_devices` вместо захардкоженного
`maxDevices: 0` — остальные три обязательных поля (`enabled: true`,
`groups`, `expireAt`) остаются в том же POST, как требует
[PLAN.md §8](../../PLAN.md).

### 6.2. Симметричное переименование в сервисе

`SubscriptionService.push_expiry` → `push_state`. Шлёт значения строки
как они есть сейчас, а не переданные вызывающим, — это свойство и было
причиной, по которой ретрай не может установить устаревшую дату.
Теперь оно распространяется и на число устройств.

### 6.3. Закрывается дыра в provision

`provision` доправляет существующий аккаунт, только если разошёлся
**срок** ([subscription_service.py:100](../../app/services/subscription_service.py:100)).
Условие становится «разошлось что-нибудь из двух»:

```python
if not created and (
    panel_user.expire_at != subscription.expires_at
    or panel_user.max_devices != subscription.max_devices
):
```

Без этого возвращающийся покупатель, чей аккаунт остался в панели с
прежним лимитом, купил бы четыре устройства и не получил их.

### 6.4. Сравниваем сырое поле

Сверка и `provision` сравнивают `panel_user.max_devices`, а не
`effective_device_limit`. Мы всегда шлём явное положительное число,
поэтому «0 = наследовать группу» для наших аккаунтов больше не
встречается, а `effective_device_limit` осмыслен только на ответе, где
группы развёрнуты, — то есть не на всех.

## 7. Поток покупки

### 7.1. Три шага вместо двух

```
buy → devices:N → tariff:<id> → provider:<id>:<name>
```

```
🛒 Купить подписку
  ├─ 👥 До 2 устройств      → devices:2
  └─ 👨‍👩‍👧 До 4 устройств     → devices:4
                               ├─ 1 месяц — 320 ₽
                               ├─ 3 месяца — 864 ₽ (выгода 10%)
                               ├─ 6 месяцев — 1536 ₽ (выгода 20%)
                               └─ 12 месяцев — 2688 ₽ (выгода 31%)
```

`TariffsRepository.list_active` получает обязательный параметр
`max_devices`. Обязательный, а не со значением по умолчанию: экран
покупки не должен иметь возможности случайно показать смешанный
список. Смешанный список ломает ярлык скидки — двухустройственный
месяц получил бы «выгоду 38%» относительно четырёхустройственного.

Кнопка «Назад» на экране тарифов ведёт в `devices:{tariff.max_devices}`
— число устройств берётся из самой строки тарифа, отдельного состояния
не заводим.

`get_sellable` остаётся единственным способом получить тариф для
продажи, на обоих шагах. Данные callback приходят от клиента и не
обязаны соответствовать нарисованной кнопке.

### 7.2. Предупреждение о понижении

Если `subscription.is_active_at(now)` истинно и `max_devices` подписки
больше выбранного, `devices:N` показывает не список тарифов, а экран.
Именно `is_active_at`, а не `status == ACTIVE`: у истёкшей подписки
терять нечего, и предупреждать там не о чем.

> У вас оплачено **до 4 устройств** до 01.10.2026 (осталось 59 дней).
>
> Если купить тариф на 2 устройства, до 2 станет и на оставшийся
> оплаченный срок — дни складываются, а число устройств задаёт
> последняя покупка.

Кнопки:

- `✅ Всё равно продолжить` → `devices:2:ok` → список тарифов
- `👨‍👩‍👧 Смотреть тарифы на 4` → `devices:4`
- `💬 Спросить в поддержке` → готовый запрос (§8)
- `↩️ Назад` → `buy`

Предупреждение показывается один раз, на самом раннем шаге, где
намерение уже известно. На экране счёта его не повторяем: там уже
назван тариф, а в его названии есть число устройств.

Понижение разрешено — это решение владельца, принятое с уже названным
последствием: человек теряет часть того, за что заплатил.

### 7.3. Число устройств применяется по последнему платежу

В `_apply_days`, внутри уже взятых блокировок и в той же транзакции,
что дни и защёлка:

```python
newest = await self._uow.payments.newest_applied_paid_at(
    payment.user_id, exclude=payment.id
)
if newest is None or payment.paid_at >= newest:
    subscription.max_devices = tariff.max_devices
```

**Почему не безусловное присваивание.** Начисление дней устроено как
«прибавить к текущему сроку», и это защищает от опоздавшего платежа:
в каком бы порядке платежи ни применились, дни складываются. Число
устройств так не работает — это присваивание.

Сценарий отказа: человек выставил счёт на 2 устройства, не оплатил,
счёт истёк. Купил тариф на 4, получил доступ. Через день старые деньги
дошли — окно `sweep_late_payments` равно семи дням, — свип поднял
платёж, и человек, заплативший за четыре устройства, получил два.

Новой колонки для этого не нужно: `payments.paid_at` и
`payments.days_applied_at` уже есть, а чтение идёт под
`lock_user` + `lock_by_user`, то есть сериализовано со всеми другими
писателями этой подписки.

`payment.paid_at` на этом шаге гарантированно не `NULL`: `_mark_paid`
проставляет его условным UPDATE раньше, чем `_provision` вызовет
`_apply_days`. Сравнение `>=`, а не `>`, — на случай, когда два платежа
получили одну и ту же секунду.

Новый метод репозитория:

```python
async def newest_applied_paid_at(
    self, user_id: int, exclude: uuid.UUID
) -> datetime | None
```

`MAX(paid_at)` по платежам пользователя, у которых
`days_applied_at IS NOT NULL`, кроме указанного.

## 8. Готовый запрос в поддержку

### 8.1. Зачем

Понижение — вероятный повод написать в поддержку, и человек будет
объяснять ситуацию своими словами, без чисел. Готовый запрос несёт
контекст, который он сам никогда не напишет.

Область строго ограничена устройствами. Общий список частых вопросов —
отдельная задача, в эту спеку не входит.

### 8.2. Ограничение, которое надо обойти

`SupportService.relay_from_user` умеет копировать **существующее
сообщение пользователя**: берёт `chat_id` + `message_id` и делает
`copy_message`. У сочинённого ботом запроса такого сообщения нет.

Добавляется второй путь доставки:

```python
async def relay_composed(self, telegram_id: int, text: str) -> RelayResult
```

Отправляет админам карточку (как обычно) и следом сам текст через
`send_message`, записывая обе строки `SupportMessage` — ответ реплаем
маршрутизируется тем же механизмом, без единой правки в
`relay_to_user`.

Анонимность не задета: правило «только `copy_message`, никогда
`forward_message`» защищает направление админ→пользователь, чтобы не
раскрыть владельца. Здесь направление обратное, и карточка и так
называет пользователя.

`_deliver_to_admin` выделяет общую часть (карточка + запись двух строк
`SupportMessage`), различается только способ доставки тела.

### 8.3. Что проверяется теми же правилами

`relay_composed` проходит те же ворота, что и обычное обращение:

- `user.support_blocked` — заблокированный не пишет и кнопкой;
- лимитер по ключу `support:{telegram_id}`, 5 сообщений в минуту, —
  иначе кнопка становится способом обойти ограничение набора текста;
- `RelayOutcome.UNDELIVERED`, если не достучались ни до кого.

### 8.4. Тексты запросов

Два, оба с числами внутри:

- **до покупки** — с экрана предупреждения: «Хочу купить тариф на 2
  устройства, но у меня оплачено до 4 до 01.10.2026. Как лучше
  поступить?»
- **после** — с экрана «Моя подписка»: «Мне нужно больше устройств,
  сейчас до 2.»

Человеку показывается подтверждение: отправили, ответим здесь же.

## 9. Триал, админская выдача, отзыв

`create_pending` получает **обязательный** параметр `max_devices`.
Обязательный намеренно: значение по умолчанию рано или поздно
досталось бы триалу молча.

- **Триал** — 2 устройства. Константа `DEFAULT_MAX_DEVICES = 2` в
  `subscription_service`, не переменная окружения: значение решено и
  новую настройку в `docs/SETUP.md` заводить незачем.
- **Админская выдача** `➕ 30 / 90 дней` меняет только срок. Если
  подписки не было — создаёт с `DEFAULT_MAX_DEVICES`. Больше устройств
  выдаётся не кнопкой, а сменой тарифа.
- **Отзыв** число устройств не трогает: `revoke` шлёт только
  `enabled: false`.

## 10. Сверка

`_reconcile_one` получает третью проверку. Расхождения разделены,
потому что лечатся по-разному:

```python
if self._expiry_differs(panel_user, subscription.expires_at):
    await self._subscriptions.extend(subscription, subscription.expires_at)
    report.expiry_fixed += 1
    return

if panel_user.max_devices != subscription.max_devices:
    await self._subscriptions.push_state(subscription)
    report.devices_fixed += 1
    return
```

Расхождение по сроку по-прежнему чинится через `extend`: один PUT
теперь выравнивает и лимит заодно. Расхождение **только** по
устройствам чинится через `push_state`, а не `extend`, потому что
`extend` обнуляет `notified_stage` — человек, которому уже ушло
напоминание «остался день», получил бы его второй раз.

`ReconcileReport` получает поле `devices_fixed`, входящее в `changed`.

Место вставки существенно: обе проверки идут **после** ранних выходов
по `revoked`. У отозванной и у истёкшей подписки аккаунт выключен, и
лимит устройств на выключенном аккаунте не значит ничего — трогать его
означало бы делать лишний запрос к панели на каждом прогоне.

**Ожидаемое поведение первого прогона после наката.** Живая подписка
владельца станет расхождением: база скажет 2, панель — 0. Сверка
пропишет явную двойку. Эффективный лимит при этом не изменится, потому
что 0 наследовало ту же двойку у группы.

## 11. Тексты

- `START`: «Подписка рассчитана на использование до 2 устройств» →
  «Подписка работает до 2 устройств, а если нужно больше — есть тарифы
  до 4.»
- Экраны подписки (`SUBSCRIPTION_ACTIVE`, `_EXPIRED`, `_PENDING`) —
  строка «Устройств: до N».
- `BUY_CHOOSE_DEVICES` — новый экран.
- `BUY_CHOOSE_TARIFF` — упоминает выбранное число устройств.
- `BUY_DOWNGRADE_WARNING` — §7.2.
- `SUPPORT_REQUEST_SENT` — подтверждение отправки.
- Админский `render_tariff` — показывает число устройств.

Везде «**до** N устройств», без обещания блокировки.
[PLAN.md §7.1](../../PLAN.md) фиксирует, почему: HWID-гейт в режиме
`permissive` обходится повторной попыткой, рантайм-лимит считает
уникальные IP в окне и при ошибке пропускает, а у Xray проверки
устройств в момент коннекта нет вообще. Обещать блокировку — обещать
то, чего система не делает.

## 12. Инварианты

Должно остаться верным после правки:

1. Одна подписка на пользователя. `UNIQUE` на `subscriptions.user_id`.
2. `panel_user_id == str(telegram_id)`.
3. База пишется и коммитится раньше панели.
4. Идемпотентность провижининга держится на `payments.days_applied_at`,
   защёлка **заявляется** условным UPDATE, а не читается.
5. Дни складываются с остатком, срок в панель уходит абсолютным.
6. Аккаунты в панели не удаляются никогда.
7. Чужие аккаунты сверка только перечисляет.
8. Пришедшая сумма не сравнивается с ценой.
9. Поддержка — только `copy_message` в направлении админ→пользователь.

## 13. Тесты

Каждый обязан **падать на коде до правки**; проверяется откатом:
убрать правку, увидеть падение, вернуть. В этом проекте уже было три
теста, проходивших и на сломанном коде.

Для новой фичи это правило требует уточнения, иначе оно ничего не
проверяет: на коде без колонки `max_devices` падает вообще всё, и
такое падение не говорит о тесте ничего. Откатывать надо **тот кусок,
на который написан тест**, оставив остальную фичу на месте. Колонка
столбца «Падает до правки» ниже называет именно этот кусок.

Интеграционные требуют настоящий PostgreSQL — SQLite игнорирует
`FOR UPDATE`.

| # | Тест | Падает до правки на |
|---|---|---|
| 1 | Покупка `m1x4` даёт `subscription.max_devices == 4`, панель получила `maxDevices: 4` | колонки нет; панель получает 0 |
| 2 | Опоздавший платёж на 2 устройства не понижает подписку, купленную на 4 позже | безусловное присваивание понижает |
| 3 | Явная покупка тарифа на 2 после тарифа на 4 понижает до 2 | сторож из №2, написанный слишком широко, заблокирует легальное понижение |
| 4 | Сверка чинит расхождение только по устройствам, `devices_fixed == 1` | проверки нет, расхождение остаётся |
| 5 | Сверка при этом **не** сбрасывает `notified_stage` | если чинить через `extend`, сбросит |
| 6 | `provision` доправляет существующий аккаунт с верной датой и неверным лимитом | условие смотрит только на дату |
| 7 | Триал даёт 2 устройства | параметр не передаётся |
| 8 | Админская выдача `+30` не меняет число устройств у подписки на 4 | если выдача начнёт передавать `max_devices` |
| 9 | Снятый с продажи `m1x4` не покупается подделанным callback | `get_sellable` уже это ловит: регрессия, падать не должна |
| 10 | Экран `devices:2` при активной подписке на 4 показывает предупреждение | если `devices:N` ведёт сразу в список тарифов |
| 11 | Готовый запрос доходит до админа, ответ реплаем возвращается пользователю | если `relay_composed` не пишет строки `SupportMessage` |
| 12 | Готовый запрос учитывается лимитером и отклоняется на шестом за минуту | если `relay_composed` не зовёт лимитер |
| 13 | Заблокированный в поддержке не отправляет готовый запрос | если `relay_composed` не смотрит `support_blocked` |

Плюс к прогону: `alembic upgrade → check → downgrade → upgrade` на
чистой базе без расхождений, `ruff check`, `ruff format --check`.

Полный прогон обязателен с `TEST_DATABASE_URL`: без него интеграционные
молча пропускаются, вывод зелёный, и проверено при этом меньше
половины.

## 14. Порядок выкатки

1. Миграция накатывается автоматически в `docker-entrypoint.sh` при
   старте контейнера.
2. Проверить строки: `select code, price_kopeks/100, max_devices from
   tariffs order by sort_order`.
3. Дождаться сверки (или запустить руками) и убедиться, что подписка
   владельца получила явную двойку.
4. Купить тариф на 4 устройства живыми деньгами и сверить с панелью.

**Ловушка.** Пересборка контейнера посреди чужой покупки убивает её без
следа: счёт исчезает, логи старого контейнера удаляются вместе с ним.
Пока владелец проверяет что-то вживую — не пересобирать.

## 15. Вне области

- создание тарифов из админки;
- общий список частых вопросов в поддержке;
- жёсткая блокировка лишних устройств, анти-шеринг;
- отложенное понижение «после окончания оплаченного»;
- перенос цен под комиссию ЮMoney — отдельное нерешённое.
